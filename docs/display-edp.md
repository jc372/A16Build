# Internal eDP panel — display, brightness, refresh rates

**State: working** with the *built display driver* option. The panel is driven by `msm`, the
backlight is controllable, and both 2880x1800 modes (120 Hz and 60 Hz) are available.

## The hardware

| | |
|---|---|
| Panel | Samsung OLED, EDID name `ATNA60HR07-0`, 2880x1800, 10 bpc, DisplayID block, 30–120 Hz |
| Link | eDP 1.4; DPCD advertises `SUPPORTED_LINK_RATES` up to 540000 (HBR2, 5.4 Gbps) and a max lane count of 4 |
| PHY | Qualcomm eDP PHY v8, `compatible = "qcom,glymur-dp-phy"`, registers at `faac00.phy` |
| Controllers | `dispcc-glymur`, `videocc-glymur`, `gpucc-glymur` (all `CONFIG_CLK_*_GLYMUR`), DP controller `af6c000.displayport-controller`, DPU `ae01000.display-controller` |
| Panel driver | `panel-samsung-atna33xc20` |
| Backlight | `dp_aux_backlight` (over AUX), registered by the panel driver once the link is up |

## What the kernel provides

When `msm` binds, everything the panel needs is upstream: `msm_dp_*`, the v8 eDP PHY, the panel
driver, and the Glymur clocks. There is **no missing driver**. Two things had to be fixed:

1. `CONFIG_CLK_GLYMUR_GPUCC` was not set in the machine's kernel, so `msm` could never bind at all
   (the GPU clock controller supplies a power domain the display's SMMU path needs). See
   [gpu-adreno.md](gpu-adreno.md) — it is a build issue, not a device-tree one.
2. The eDP link would not train. That is this page's subject.

## The failure

With the display drivers loaded, the link fails at the second training phase, every time:

    max_lanes=4 max_link_rate=810000
    link_rate=540000                               <- msm picks the highest rate the *sink* lists
    rate=540000, num_lanes=4, pixel_rate=709633
    using LINK_BW_SET: 0x14                        <- HBR2
    link training #1 on phy 0 successful           <- clock recovery fine, all 4 lanes
    link training #2 on phy 0 failed. ret=-110     <- channel equalization never converges
    DPCD 0x202: 11 11 80 04 22 22  ->  11 11 00 04 44 44
                                                   (CR done, no EQ, no symbol lock; adjust
                                                    0x22 then 0x44 = swing 0 / pre-emphasis 1)
    msm_dp_aux_isr: Unexpected DP AUX IRQ 0x01000000   (= DP_INTR_PLL_UNLOCKED, while idle)

`-110` here is a **link-training equalization timeout** (`msm_dp_ctrl_link_train_2()`,
`dp_ctrl.c:1626`), not an AUX timeout.

## Root cause

The v8 PHY's power-on programming sequence is only valid for 4-lane 8.1 G, as the person who wrote
it says in the posting of the fix:

> The programming sequences introduced for v8 doesn't work other than for 4-lane 8.1Gbps. For
> 2-lane 5.4Gbps link training fails and for 2.7 and 1.62Gbps PLL lock isn't reached.

Our panel's advertised rate list stops at 5.4 G, so `msm_dp_panel_read_link_caps()` picks exactly
the broken case. Independently, another A16 owner's rate sweep on this panel model found the same
shape: *RBR/HBR fail clock recovery, HBR2 passes CR and fails EQ, HBR3 trains and the panel lights.*

## The fix we carry

Take the highest rate the **device tree** allows instead of the highest the sink advertises. The
DT's `link-frequencies` already reach 8.1 G, so nothing in the DT needed changing.

## The posted v8 PHY series we also carry

The posted-but-unmerged series from Bjorn Andersson teaches the v8 PHY to program itself per
version. It does **not** fix our case by itself (we tested it as the live PHY module: identical
failure at 4-lane HBR2 — the series covers 2-lane 5.4 and 4-lane 8.1, not 4-lane 5.4), but it is a
strict improvement and it is the right long-term shape, so we carry it and the kernel we build
contains it.

**What this machine adds:** the series' own description lists 2-lane 5.4 G as broken. On this
machine **4-lane 5.4 G** fails the same way (CR clean, EQ timeout, adjust requests climbing to
swing 0 / pre-emphasis 1), while 4-lane 8.1 G trains with the *stock* sequence. The series is worth
carrying regardless: it makes the PHY program itself per version rather than per rate.

## Retired experiments

Kept in `patches/retired/`, all with identical failures, so nobody repeats them:

- `0004` — point the eDP path at the v8 (Glymur) drive table: no change.
- `0005` — `TXn_TRAN_DRVR_EMP_EN` from `0x01` to `0x5f` (the value Qualcomm's combo PHY uses for
  this PHY generation): no change.

Also ruled out, from the debug boot (`drm.debug=0x1ff`, 15 894 DRM lines):

- lane wiring — the `af6c000` endpoint is `data-lanes = <0 1 2 3>`; the "data-lanes not defined"
  warnings in the log come from the three external USB-C controllers, not the panel
- TPS3 as the pattern — correct (`drm_dp_tps3_supported()` reads `DP_MAX_LANE_COUNT` bit 6, which
  this panel sets; the driver writes `DPCD 0x102 = 0x23`)
- disabling the scrambler for TPS2/TPS3 — that is what i915 does as well
- power and clock mechanics, all verifiably good: `gpio18 out high` (panel `enable-gpios`),
  `VREG_EDP_3P3` at 3300 mV, `faac00.phy-vdda-phy` 21 mA and `-vdda-pll` 36 mA, `dptx3_link_clk`
  540 MHz, `dptx3_pixel0_clk` 532 MHz, `dptx3_aux_clk` 19.2 MHz, `faac00.phy::vco_div_clk` 1.35 GHz,
  `tcsr_edp_clkref_en` on
- a newer kernel: today's linux-next has identical `dp_ctrl.c`, `dp_link.c`, `dp_panel.c`,
  `panel-samsung-atna33xc20.c`, `phy-qcom-edp.c`; only the unrelated USB-C
  `phy-qcom-qmp-combo.c` differs. Upstream also carries a DT for this exact laptop
  (`glymur-asus-zenbook-a16-ux3607oa.dts`) which builds byte-identical to the machine's stock DTB,
  so this is upstream code that nobody has hit before.

## Still open

- **Brightness keys**: with `acpi=off` the EC has no driver, so no `KEY_BRIGHTNESS*` input device
  exists. The GNOME slider writes through `dp_aux_backlight` and works; the Fn keys do not.
- **External outputs**: working as of 2026-10-02 — USB-C DP with the link rate capped at the sink's own 5.4 Gbps, HDMI at 5120x1440 — see [display-outputs.md](display-outputs.md).
- **The permanent form of the fix**: the v8 PHY series, plus a statement in the device tree or the
  driver that 8.1 G is the usable rate for this PHY revision and panel. Our `patches/0009` is a
  working experiment, deliberately written as the smallest possible change.
