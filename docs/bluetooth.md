# Bluetooth — WCN7850-class combo, attached over UART

**State: working.** Controller `3C:EF:A5:29:6A:62` is up, `hci0` scans and pairs.

## The hardware

| | |
|---|---|
| Part | Qualcomm WCN7850-class combo; BT side reached over UART (serdev), PCI id `17cb:1112` |
| Adapter identity | chip PID `0x20`, SOC `0x40292100`, ROM `0x00000101`, patch `0x7b40` — **HMT/HAMILTON** |
| Firmware in use | `/lib/firmware/qca/hmtbtfw20.tlv` (280 764 B) with `hmtnv20.b105/b10f/b112/b3b` (9 656 B) |
| Firmware missing | `qca/hmtbtfw11.tlv` (the *rampatch*) — the driver logs `-2` and runs on ROM firmware, which works |

## The two changes

### 1. The UART needs a serdev client describing the chip

The BT chip sits on `uart14`, but nothing told the kernel what was on it, so no serdev client was
created and no `hci0` ever appeared. The fix is the usual Qualcomm shape: a `bluetooth` child node
with the right compatible and supplies. It also needs the six BT regulator rails, because the combo
is powered from fixed regulators that the upstream DTS does not describe for this board.

### 2. `W_DISABLE2#` was being left asserted

Even with the serdev client in place the chip never answered:

    hci0: command 0xfc00 tx timeout
    Bluetooth: Reading QCA version information failed (-110)

`drivers/power/sequencing/pwrseq-pcie-m2.c` requests the line as

    ctx->w_disable2_gpio = devm_gpiod_get_optional(dev, "w-disable2", GPIOD_OUT_HIGH);

while the machine's device tree marks the same line `ACTIVE_LOW`, so `GPIOD_OUT_HIGH` drives it *low*
— i.e. asserted, holding the combo disabled. Flipping the device-tree flag to `ACTIVE_HIGH` (the
electrical equivalent of deasserting it) makes BT come up. The driver-side alternative — requesting the
line `OUT_LOW` instead — is a larger change; what is here is the smallest change that works, and it
lives in the device tree.

## The patch we carry

Applied to the machine's device tree. Note the form: this is a diff against the **decompiled DTB**
(the machine boots a DTB blob, so that is where the change had to land), which is why the property
values are numeric (`0x1be`) rather than labels. The equivalent change at *source* level in the
upstream DTS — same nodes, same values, but with phandles and `regulator-bt-*` labels — is the form
that belongs in the DT source; see "still open" below.

## How it was applied, and how to re-apply it

`BRINGUP/tools/a16-bt-arm.sh` arms a patched DTB by placing it over **both** stock DTB paths
(`/boot/glymur-asus-zenbook-a16-ux3607oa.dtb` and its ESP copy), keeping the untouched original as
`.a16stock`. `BRINGUP/tools/a16-bt-setup.sh status` identifies which DTB is live by decompiling it
and looking for `qcom,wcn7850-bt`.

The live DTB differs from the stock one by **exactly the three things in patch 0001**, which is easy
to confirm with `dtc` on both:

    dtc -I dtb -O dts /boot/glymur-asus-zenbook-a16-ux3607oa.dtb.a16stock > /tmp/stock.dts
    dtc -I dtb -O dts /boot/glymur-asus-zenbook-a16-ux3607oa.dtb          > /tmp/live.dts
    diff /tmp/stock.dts /tmp/live.dts

    stock: wcn7850-bt nodes=0  regulator-bt rails=0  w-disable2-gpios = <0x58 0x74 0x01>
    live : wcn7850-bt nodes=1  regulator-bt rails=6  w-disable2-gpios = <0x58 0x74 0x00>

    live DTB sha256: d8fe1c623d65f5ad…   stock: ddb423f8dda683a9…

The polarity hunk is the one that turned the `-110` version timeouts into a working controller; the
serdev node and the six supplies are what make the chip attach at all. Both are in the patch, and
`scripts/a16-bootstrap.sh --options` arms the patched DTB from the copy kept in `firmware/`.

## Verify

    hciconfig -a        # or: bluetoothctl show
    dmesg | grep -iE 'hci0|btqca|hmtbtfw'
    printf 'show\n' | bluetoothctl | head

Expected: `hci0` up, address `3C:EF:A5:29:6A:62`, and a `Reading QCA version information` line that
does **not** end in `-110`.

## Still open

- **Source-level DT patch.** The working change lives in a decompiled DTB. The clean deliverable is
  the same change against `arch/arm64/boot/dts/qcom/glymur-asus-zenbook-a16-ux3607oa.dts` in
  linux-next, as a `bluetooth { ... }` child of `&uart14` plus the six `regulator-bt-*` rails, and
  the `w-disable2-gpios` polarity fix — buildable with
  `make ARCH=arm64 qcom/glymur-asus-zenbook-a16-ux3607oa.dtb` and comparable against the working DTB.
  Drafting it is the next step for this component; it is the only piece of the BT work that is not yet in a form that can be applied directly.
- **The rampatch**: `qca/hmtbtfw11.tlv` is absent from the firmware package on this system, so the
  chip runs from ROM firmware with the `hmtbtfw20.tlv` patch. Works, but worth having.
- **`pwrseq-pcie-m2` and PCI id `17cb:1112`**: the driver's per-device data does not cover this id,
  so no UART-enable sequence is run for it (it does run for `17cb:1103`/`17cb:1107`). That is likely
  the proper home for the polarity fix.
