NOTES
For me, not for the mail.  What the terms mean and why the gaps are the gaps.
==============================================================================

MAILBOX
  "Mailbox" is the driver's own word, not mine.  ASUS_EC_PAGE_MAILBOX 0xc4 is
  an EC register page; it holds ASUS_EC_MBOX_REG_CMD 0x30, SUBCMD 0x31 and
  DATA 0x32, and the helpers are asus_ec_wait_mailbox() and
  asus_ec_mailbox_cmd().  "MBOX" in the identifiers is just his abbreviation.

  It is the EC's paged register window -- the driver reaches the EC through
  asus_ec_readb(ec, page, reg, &out) / asus_ec_writeb(ec, page, reg, data).
  It is NOT the kernel mailbox framework: no <linux/mailbox.h>, no mbox_chan,
  no provider/consumer binding.  "Mailbox" in a kernel context usually means
  that framework, so if he ever asks for comments on the driver, the name is a
  fair thing to flag.

  A command is submitted by writing SUBCMD, then DATA, then CMD, and polling
  CMD until the EC clears it to zero -- five tries, 5 ms apart.  Page 0xc6 is
  the temperature page, holding the CPU sensor at 0xa6 and the SoC at 0x2a.

SUSPEND AND RESUME
  These are dev_pm_ops callbacks, not runtime PM.  Each calls
  asus_glymur_ec_modern_standby(), which is a single i2c_smbus_write_byte_data
  to 0x76 with 0x23 as command and 0x07 or 0x08 as the value, and returns its
  result.  The return value is what makes this checkable: the PM core aborts a
  suspend whose device callback fails, so a completed cycle cannot be hiding a
  failed EC write.  That is why a clean suspend is itself evidence.

WHY THE EVENT PATH IS THE ONLY GAP
  asus_ec_irq() reads ASUS_QCOM_EC_EVENT_CMD 0x05 and logs the code with
  dev_dbg_ratelimited.  Nothing prints at the default log level, so there is no
  way to tell from a normal boot whether the EC ever raises an event.  Raising
  the log level would need CONFIG_DYNAMIC_DEBUG and dyndbg on the kernel
  command line -- more than a test report needs, but possible.

WHY THE MAILBOX IS NOT IN THE "NOT TESTED" LIST
  asus_ec_enable_writes() sends MBOX_CMD_MISC 0x02 / SUBCMD_MISC_ENABLE 0x83
  during probe, and the probe aborts if it returns an error.  The driver binds,
  so that command succeeded.  It is proven, not untested.  The keyboard
  backlight level goes through the same mailbox (CMD_KBD 0x01 / SUBCMD_KBD_LVL
  0x87), which is why setting the backlight is also evidence the mailbox works.

WHY THE LID SWITCH AND POWER BUTTON ARE NOT MENTIONED
  An earlier draft listed them as untested.  They are not his: asus-glymur-ec.c
  contains no lid or power-button code at all, and the board dts handles both
  through gpio-keys.  Listing them would imply his driver covers them.

WHY THE TREE DETAILS MATTER TO HIM
  The board dts file his patch 3/3 touches also carries unrelated local patches
  of ours -- Bluetooth serdev and regulators, an RTC property, and the HDMI
  power-domain workaround below -- none of which touch his &i2c9 hunk.  A
  maintainer reading our tree would see them, so the mail says so.
