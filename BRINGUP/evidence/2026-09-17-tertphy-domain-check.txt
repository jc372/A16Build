Why — the consumer deferred and never finished probing:

  platform a000000.usb: deferred probe pending: dwc3-qcom: failed to register DWC3 Core

That message is `dev_err_probe()` after `dwc3_core_probe()` failed in `dwc3_qcom_probe()`
(drivers/usb/dwc3/dwc3-qcom.c:710); the device is on the deferred-probe list, i.e. the driver
returned -EPROBE_DEFER — it is waiting on the same combo PHY that cannot come up. So
`genpd_dev_pm_attach()` never powers the domain: nothing in the DT is bound to it.

Consequence for the theory: lever 1 (a disabled-but-present controller) is a dead end, because
this consumer can never bind. It does not by itself say the domain is innocent.

Second lever, staged in the same tool and not yet booted (2026-09-17 11:32):
`sudo bash ~/a16.sh tertphy arm bridge` adds a *single* `power-domains = <&gcc GCC_USB30_TERT_GDSC>`
to `/hdmi-bridge` (`parade,ps185hdm`, driver `simple-bridge`, which binds on every boot). The
platform bus calls `dev_pm_domain_attach(dev, true)` before probe, and with exactly one
power-domain specifier `genpd_dev_pm_attach()` calls `genpd_power_on()`
(drivers/pmdomain/core.c:3411) — so the domain is forced on at attach with no dependency on
dwc3-qcom. A device with two or more specifiers is skipped by that path (core.c:3457), which is
why this cannot simply be appended to `phy@88e1000`, which already has one.

Verified without touching /boot: arm/revert were run against a copy of the DTB in /tmp
(`A16_DT_FILES=...`), writing `72 18` (raw `48 12`) — byte-identical to the usb node's specifier —
idempotent on a second run, and `revert` restores both levers.

Conclusion: the tert combo PHY's COM clock was only unpowered (the hypothesis item 10 was built on).
The fix is a machine-DTS change — the domain needs a consumer (or an always-on/keepalive vote) —
not the upstream PHY programming series. What is not yet proven is an actual output: no monitor has
been through it since, and the connector stays `disconnected` with nothing plugged. Next test:
`sudo bash ~/a16.sh display watch` over SSH, plug a monitor into HDMI, watch for link training; if
the picture freezes instead, the kernel survives and `sudo bash ~/a16.sh display recover` (monitor
unplugged) rebuilds the desktop — patch 0008 is the insurance if a failed enable tries to push idle
into a controller that never came up.
